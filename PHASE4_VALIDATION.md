# Phase 4 — External Developer Validation

**Status: complete (simulated).** This phase validated agent-blame the way an
external-developer study would, with one explicit limitation: this
environment has **no access to human participants**, so the study was run as
the closest rigorous equivalent — simulated first-use sessions reconstructed
from `--help`/README knowledge (with real command execution), measured
time-to-answer vs manual Git, and trust calibration against Git-verified
ground truth. A ready-to-run protocol for real developers is included at the
end. **No developer quotes in this document are from real people.**

Machine-readable dataset: `validation_dataset.json` (generated by
`_validate_phase4.py`).

---

## 1. Executive summary

Phase 4 found **one genuine correctness bug** (false DIRECT callers from
import-alias bare calls — requests `prepare_url` gained 4 fabricated
callers), **two output-quality problems** (a 528-line evidence dump on a
long-lived file; MODIFIED callers rendered with the "dead" marker), and
verified the rest of the system against Git ground truth. All three were
fixed with regression tests and logged per the workflow. **Final: 279 tests
green** (was 270). The honest headline findings:

- **Discoverability is excellent.** All 19 first-use probes behaved
  correctly; every mode is findable from `--help`; every common mistake gets
  a clear diagnostic.
- **The tool is not faster than a known `git` command.** For a git expert
  with a precise question, raw `git blame` (0.02 s) beats a full agent-blame
  run (0.8–2.0 s) in wall clock. The value is **effort**, not speed: knowing
  which commands to run, classifying 5–24 raw grep hits, connecting movement
  chains, and aggregating evidence.
- **The output was too long before the fix** (528 lines on rich's
  `Console.print`, ~95% near-identical evidence) — now 82 lines with zero
  information loss (JSON keeps everything).
- **False-authority testing found a real false caller** — exactly the class
  of bug this phase exists to catch. Fixed.
- MVP classification: **USEFUL MVP (C)** — unchanged, but the Phase 4 fixes
  removed the most dangerous remaining false-confidence source.

### Persona 1 — experienced Git user (Task B: before modifying `Session.request`)
- Natural manual probe: `git blame -L 324,324` + `git log --oneline` — both
  returned raw facts in 0.04 s total.
- agent-blame first command (`sessions.py:324`): 0.57 s, answer visible in
  the first 12 lines (`introduced by 561e4b68` + 13 evidence items).
- Behavior recorded: a git expert would still verify with `git blame` — the
  tool is a discovery layer, not a Git replacement. That is expected and is
  not a failure (spec §8).

### Persona 2 — normal professional developer (Task A: why does `dispatch_request` exist)
- First command from `--help`: `src/flask/app.py:969` → 1.04 s, HIGH, fact +
  inference + 27 evidence items, then `--history` for the timeline.
- The `--history` full chain (240 lines) is the correct answer for HISTORY
  mode; WHY mode now caps it (70 lines).

### Persona 3 — developer who rarely investigates Git history (Task E: unfamiliar code)
- Single command `rich/console.py:1891` → 1.23 s. **Pre-fix output was
  528 lines** — a rarely-investigating user would skip ~95% of it. **Post-fix:
  82 lines**, answer first, all sections readable. This was the single
  clearest UX problem found.

## 4. Time-to-answer: normal Git vs agent-blame (measured)

| Question | Manual Git | agent-blame |
|----------|-----------|-------------|
| Where did this code come from? | 3 cmds / 0.06 s | 1 cmd / 0.8 s |
| Who calls this function? | 2 cmds / 0.04 s + **manual classification of 5–24 raw hits** | 1 cmd / 0.8 s |
| Was this code moved here? | 2 cmds / 0.08 s (raw rename list — origin still needs digging) | 1 cmd / 1.2 s (full origin chain) |
| What did this commit change? | 2 cmds / 0.04 s | 1 cmd / 2.0 s |
| What should I know before modifying? | 3 cmds / 0.09 s (raw facts only — no callers/risk/regressions) | 1 cmd / 1.0 s |
| **Full 5-question investigation** | **12 cmds / 0.3 s** | **5 cmds / 6.0 s** |

**Honest interpretation (spec §8):** agent-blame is *not* a wall-clock win
for a git expert who already knows exactly which commands to run. It wins on
**archaeology effort**: the "who calls this" question requires manually
classifying 5–24 raw `git grep` hits (comments/strings/unrelated
identifiers), the movement question requires multi-command origin tracing,
and "what should I know before modifying" is not answerable by the manual
command set at all (no caller/risk/regression aggregation). The correct
positioning is **discovery + aggregation layer**, and the product should
never advertise itself as "faster than git blame".

## 6. Bugs discovered → fixed (all logged before fixing)

1. **False DIRECT callers (correctness — the phase's most important find).**
   `_classify_call` never verified the callee name; the discover-loop
   pre-filter admits any call whose name is an import alias, and the
   bare-call branch then returned `DIRECT_CALL` for *any* bare call inside
   the target's class. On requests, `prepare_url` gained 4 fabricated DIRECT
   callers (`prepare_auth`, `prepare_body`, `prepare_cookies`, a bogus
   self-call at line 511) from `cast(...)` / `parse_url(...)` calls, plus 4
   bogus POSSIBLE entries. flask/rich carried the same noise. **Fix:** a
   final-name guard — a call is only a caller of our symbol when its callee
   name IS the target's name or is a bare from-import alias that
   deterministically resolves to the target. After the fix requests reports
   exactly 1 DIRECT caller (line 441, verified), flask exactly 1
   (full_dispatch_request:1019, verified). The deleted-caller fixture had
   been asserting a false self-caller and now tests the real DELETED-status
   mechanism. (+2 tests)

2. **Output noise (UX, measured).** WHY/HISTORY/RISK rendered every
   per-commit `modified_by` bullet individually; rich's `Console.print` →
   528 lines, 199 near-identical "later commit ... modified the file" lines,
   callers listed twice (Evidence + Callers), chain dumped 201 lines. The
   diff/commit renderers already aggregated (the tool's own "noise-control
   contract") — the main renderer didn't. **Fix:** route the main renderer
   through `_render_evidence_aggregated`; drop caller evidence kinds from
   Evidence when the Callers section renders them; cap the WHY/RISK chain at
   25 with a pointer to `--history`. rich: **528 → 82 lines**; sessions.py:
   251 → 65. JSON unchanged (full per-commit detail preserved). (+4 tests)

3. **MODIFIED callers rendered as dead (UX, misleading).**
   `_render_callers` marked every non-LIVE status `✗`; in `--diff` on a
   modified file this contradicted the risk wording ("13 confirmed live
   caller(s)") and implied callers were dead when they exist at HEAD.
   **Fix:** distinct markers — `✓` LIVE, `~` MODIFIED (exists, file is part
   of the change), `✗` DELETED (the only dead status). (+3 tests)

**Total: +9 tests, 270 → 279.**

## 8. Security / determinism status

- **JSON determinism:** two runs of flask app.py:969 --json are
  **byte-identical** (same sha1); JSON contains no control characters.
- **Security sweep:** no shell=True / os.system / eval / exec of repository
  content; argv-only git; `-z` parsing; sanitized terminal output (ANSI,
  C0, C1, DEL). Unchanged from Phase 3; caller scan is AST-parse-only.
- The new `--diff` test ran against a scratch clone; real repos stayed clean.

## 10. Killer use case

**WHY with movement correction** ("moved here by d63e94f5, originally
introduced by 2b34880e") — verified against git. This is the question normal
`git blame` answers wrong (it reports the last modifier), and it is the
answer developers most need when meeting unfamiliar code. Second: **--diff
before submitting** (symbol resolution + callers + historical risk for the
exact lines being changed).

## 11. Weakest use case

**REGRESSION detection.** It is honest (explicit-revert evidence is real;
everything else is LOW/POSSIBLE with documented caveats) and produces zero
false positives on the Phase 4 targets, but on revert-free repos it adds a
section that says nothing. It should stay as contextual evidence in every
mode (not a standalone mode) and is correctly documented as best-effort.

## 13. Final MVP classification

**USEFUL MVP (C).** Same letter as Phase 3, but the Phase 4 fixes removed
the most dangerous remaining false-confidence source (fabricated callers)
and the biggest usability barrier (evidence dumps). The system now:

- answers WHY/HISTORY/RISK/DIFF/COMMIT correctly on four real repos,
- admits INSUFFICIENT when it does not know,
- never claims "unused" / "safe" / causation,
- is discoverable from `--help` alone,
- produces output a developer can read in one screen.

It is **not** ready for broader release (E): caller analysis is Python-only,
merge interpretation is first-parent, and a real developer study has not yet
been run.

## 14. Ready-to-run protocol for real developers (5 participants)

1. Give each developer `--help` and one task (A–E from the phase spec) on
   one repo. Do not explain the internals.
2. Record: first command, first successful command, time-to-answer, sections
   read vs skipped, whether they run `git` afterward.
3. Ask the 15 questions in the phase spec (open-ended; no leading).
4. For every answer they rely on, have them verify with `git blame`/`git
   show` and rate their confidence vs ground truth.
5. Score the product scorecard (usefulness, ease, accuracy, trust,
   time-saved, explainability, distinctiveness, reuse, recommend) with
   evidence per score.
6. Report back; this document's findings should be rechecked against real
   behavior — especially the wall-clock trade-off (§4), which real
   developers may weight differently than the effort argument.
